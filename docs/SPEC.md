# Chords Listener — shared spec & contracts

Local web app: paste a YouTube (or any yt-dlp-supported) URL, drop an audio/video file, or record from mic → the app detects chords and shows them in a beautiful, interactive, play-along UI where chords are easy to read and copy.

Everything runs on `localhost`. Target machine: macOS arm64 (Apple M4 Pro), ffmpeg 9 at `/opt/homebrew/bin/ffmpeg`, node 22, uv.

## Layout

```
chords-listener/
  backend/            Python 3.11, uv project (run everything with `uv run ...` from backend/)
    app/
      main.py         FastAPI app (API agent)
      jobs.py, sources.py, storage.py, models.py   (API agent)
      engine/         chord recognition engine (Engine agent) — public API in engine/__init__.py
    tests/            pytest
    scripts/          eval / tooling scripts
  frontend/           Vite + React 19 + TS + Tailwind v4 + zustand + framer-motion + lucide-react
  data/               runtime storage (gitignored): data/tracks/<trackId>/...
  docs/SPEC.md        this file
```

Ports: backend `127.0.0.1:8765`. Vite dev `5173` proxies `/api` → backend. In "prod" mode the backend serves `frontend/dist` at `/` (SPA fallback) so the whole app is `http://localhost:8765`.

## JSON conventions

All API JSON uses **camelCase** keys exactly as in `frontend/src/types.ts` (the source of truth for shapes). Times are seconds (float). Ids are lowercase hex strings.

## Chord label convention (engine output == frontend parser input)

`label = <root><suffix>[/<bass>]`, or `"N"` for no-chord (silence / non-harmonic).

- root / bass spelled with **sharps**: `C C# D D# E F F# G G# A A# B` (frontend re-spells by key / user preference).
- `quality` field (canonical) → suffix in label:

| quality | suffix | example |
|---|---|---|
| maj | `` | `C` |
| min | `m` | `Cm` |
| 7 | `7` | `C7` |
| maj7 | `maj7` | `Cmaj7` |
| min7 | `m7` | `Cm7` |
| dim | `dim` | `Cdim` |
| aug | `aug` | `Caug` |
| sus2 | `sus2` | `Csus2` |
| sus4 | `sus4` | `Csus4` |
| dim7 | `dim7` | `Cdim7` |
| hdim7 | `m7b5` | `Cm7b5` |
| 6 | `6` | `C6` |
| min6 | `m6` | `Cm6` |
| 9 | `9` | `C9` |
| add9 | `add9` | `Cadd9` |

The engine may output any subset (maj/min at minimum). For `N`, `root`/`quality`/`bass` are `null`.

## Engine contract (`backend/app/engine/__init__.py`)

```python
ProgressFn = Callable[[float, str], None]   # (fraction 0..1 within analysis, short stage message)

def engine_info() -> dict:
    # {"name": str, "version": str, "features": {"separation": bool, "downbeats": bool, ...}}

def analyze(audio_path: str, progress: ProgressFn | None = None, options: dict | None = None) -> dict:
    # audio_path: ANY file ffmpeg can decode (mp3/m4a/wav/flac/ogg/opus/webm/mp4/mov...). Engine decodes it itself.
    # options: {"separate": bool} (ignored if unsupported) — unknown keys ignored.
    # returns (camelCase):
    # {
    #   "duration": float, "tempo": float, "timeSignature": int (usually 4),
    #   "beats": [float...], "downbeats": [float...],
    #   "chords": [{"start","end","label","root","quality","bass","confidence"}...],  # contiguous, sorted, cover 0..duration
    #   "key": {"tonic": "A", "mode": "minor", "name": "Am", "confidence": float},
    #   "waveform": [float 0..1] (~1200 peaks),
    #   "engine": "name version"
    # }
```

Must be thread-safe (called from a worker thread) and must never import torch/heavy optional deps unless an option requires it.

## HTTP API (`/api`)

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/api/health` | – | `Health` |
| POST | `/api/jobs` | `{"url": str, "options"?: {"separate"?: bool}, "clip"?: {"start": int}}` | `Job` (201). If the same source was already analyzed → job is immediately `done` with `trackId`. `clip` below. |
| POST | `/api/jobs/upload` | multipart `file` (+ optional form field `options` JSON) | `Job` (201) — dedup by content sha1 |
| GET | `/api/jobs` | – | `Job[]` (active + recent, newest first) |
| GET | `/api/jobs/{jobId}` | – | `Job` (frontend polls every 1 s, 3 s in a hidden tab) |
| POST | `/api/jobs/{jobId}/cancel` | – | `Job`. The job stops at its next progress report and ends with `errorCode: "cancelled"`; a finished job is returned unchanged; 404 `not_found` for an unknown job (or another user's). |
| GET | `/api/tracks` | – | `TrackSummary[]` newest first |
| GET | `/api/tracks/{id}` | – | `Track` |
| PATCH | `/api/tracks/{id}` | `{"title"?: str, "artist"?: str, "chords"?: ChordSegment[]}` | `Track` (user edits; sets `edited: true`; original detection kept on disk) |
| POST | `/api/tracks/{id}/reset` | – | `Track` (drop user chord edits) |
| POST | `/api/tracks/{id}/reanalyze` | `{"options"?: {...}}` | `Job` |
| DELETE | `/api/tracks/{id}` | – | 204 |
| GET | `/api/tracks/{id}/audio` | – | playback audio (mp3), **must support HTTP Range** (seeking) |
| GET | `/api/tracks/{id}/notes` | – | `TrackNotes` (live piano, see below); 404 `not_found` while not computed yet (or unknown track) |
| PUT | `/api/tracks/{id}/notes` | `TrackNotes` | 204; stores / replaces them. 422 `internal` when invalid, 413 `too_large` over 25 MB, 404 unknown track |

`POST /api/jobs` with `clip: {start}` (whole seconds, optional): only `CHORDS_YT_CLIP_S` (30) seconds of a YouTube video from `start` (0..86400); the job and the track carry `clip: {start, end}`; 400 `invalid_url` for a non-YouTube link, 501 `unavailable` when the server can't download fragments (cloud without `CHORDS_FETCH_URL`). The cloud asks the `chords-fetch` service for the fragment (docs/CLOUD.md → YouTube clips); a failed Google ID token for it, or a fetch that stays busy for 60 s, is a `download_failed` job, not a crash.

Errors: `{"detail": str, "code": ErrorCode}` with proper HTTP status. Job failures: `status: "error"`, `errorCode`, `error` (human message, English; frontend maps `errorCode` → localized text).

`ErrorCode`: `invalid_url | download_failed | unsupported_format | too_long | too_large | analysis_failed | not_found | internal`.

Job progress mapping (overall `progress` 0..1): queued 0 → downloading 0–0.35 → decoding/transcoding 0.35–0.45 → analyzing 0.45–1.0 (engine fraction scaled) → done 1.

Limits (env-overridable): `CHORDS_MAX_DURATION_MIN=30`, `CHORDS_MAX_UPLOAD_MB=500`, `CHORDS_DATA_DIR=<project>/data`.

### Where the API lives (same origin / cloud / remote / browser mode)

The UI is also published as a static site (GitHub Pages, `VITE_BASE=/chords-listener/` build). `src/lib/serverMode.ts` picks the API in this order (`candidateList`) and `src/lib/api.ts` routes every call; callers never build URLs themselves. `useConnection` = `{ status: 'checking' | 'server' | 'browser', backend: 'local' | 'cloud' | null, apiBase, … }`.

- **Same origin** (local builds): `/api` (served by the backend or the Vite proxy).
- **Cloud** (signed in, `CLOUD_API_URL` in `src/config.ts` set): `<cloud>/api`, see docs/CLOUD.md. Selected at once, without a request (any request wakes a Cloud Run instance): `/health` is asked only when needed — the mode popover opens, a vocal transcription is started while vocals support is unknown (the features of the last check are kept 24 h in localStorage), a request failed at the network level — and never polled; on load `GET /jobs` is asked only when a job started on this device in the last 2 h may still run (`src/lib/cloud/activity.ts`). Opening a song (also in the score view) asks nothing about vocals when its track says `vocals: false`, and looks for a running vocals job by the same 2 h rule. The header says «waking» only while the cloud is actually being asked. Every call but `/health` carries `Authorization: Bearer <Firebase ID token>`; a 401 renews the token once, then asks the user to sign in again (`requestSignIn`) and repeats the call; 429 → `quota_exceeded`. Uploads go to Firebase Storage `users/{uid}/uploads/{uploadId}/{filename}` (resumable) and then `POST /jobs/storage` (`src/lib/cloud/storage.ts`); small files fall back to multipart when Storage refuses. Signed media URLs are resolved against the cloud origin.
- **Remote** (opt-in `useServerPrefs.localServer`, always on in local builds): `settings.serverUrl` (default `http://localhost:8765`). URLs the server returns (`audioUrl`, relative thumbnails) are resolved against it. Probed on load and every 10 s while down; on a public https page Chrome's Local Network Access permission is required, so with permission state `prompt` the server is probed only on a user click.
- **Browser mode** (no server): files and recordings are analyzed in the page (`src/lib/engine`), stored in IndexedDB (`src/lib/local`). Ids start with `local-` (tracks) / `local-job-` (jobs) and are served by the browser library in every mode; jobs go `queued → decoding → analyzing → done` with the same progress ranges. `createJob` (links) rejects with client code `server_required`; `startLink` decides first (`linkTarget` in `components/input/url.ts`): a local server (`backend: 'local'`) downloads every link; signed in on the cloud, a YouTube video opens the fragment picker (`#/youtube/<videoId>[?t=<s>]`, the link's own `t=` as the default start) and «Розібрати акорди» sends `POST /api/jobs {url, clip: {start}}` (`createClipJob`); without an account it opens "listen in the tab" (`#/listen/youtube/<videoId>[?blocked=1][&t=<s>]`). A YouTube page that is not one video (playlist, channel) is `notVideo`: a hint, nothing sent. Other sites go to a connected server, otherwise ask for an account. A fragment job that ends in `download_blocked`, or a cloud that answers 501 `unavailable` to a fragment, opens "listen in the tab" at the fragment's start. The picker (`components/clip/ClipPage.tsx`) learns the video's length as soon as the player knows it (phones often only after play starts, and says so: «Увімкни відео на мить…»); with a non-embeddable video it still offers «Розібрати акорди» from `?t=` or 0. The start is capped at 86400 s (`MAX_CLIP_START_S`, the server's limit). Fragment tracks carry `clip: {start, end}` (video seconds) and `startOffset = start`: the player starts at `clip.start` and pauses at `clip.end`, and play on a track paused at its end restarts from its start (`components/player/clipBounds.ts`); the title shows the range (`Назва · 1:12–1:42`). Tab recordings of a video keep `source: {type: 'youtube'}`; a recording that began at video time t > 0 is stored with t seconds of silence in front, so its times are video times.
- Backend: `CHORDS_ALLOWED_ORIGINS` (comma-separated, default `https://shchadylotaras.github.io` + the Vite dev origins) may use the API cross-origin (CORS, Private Network Access preflight, cross-site write check); pages on a local host (any port) always may.

**Live library** (`src/lib/cloud/library.ts`, `src/lib/cloud/files.ts`; the server side is docs/CLOUD.md "Library in Firestore"). While `backend === 'cloud'` and someone is signed in, `src/lib/api.ts` reads the library without the cloud API, so neither opening the site nor opening a song wakes a Cloud Run instance:
- the list is the account's Firestore index `users/{uid}/tracks` (one `onSnapshot` listener with metadata changes, on the shared memory-cache instance of `src/lib/firestore.ts`; started by `src/lib/cloud/libraryWatch.ts`, stopped and emptied synchronously on sign-out or when another account signs in). A change made on any device shows at once: `components/history/tracksStore.ts` refreshes on every new list, and once more when the index fails (the API path takes over); a metadata-only snapshot (online ↔ offline) writes nothing. Before the index's first answer the home page shows the list kept on the device while the list waits for that answer up to 3 s (`LIBRARY_WAIT_MS`), and so does opening a track or its notes (leaving the track ends its wait). An index that did not answer in time is not waited for again: reads take the API path at once until it answers, fails or starts again (another sign-in). An index that answers is the whole list: a track without an index document is not listed (opened by its link it comes from the API), so the site is deployed only after a verified backfill (docs/CLOUD.md "Rollout order and backfill");
- an opened track is `track.json` from Storage (`getBytes`, owner-only rules), its audio and stems streamed through the download-token URLs built from its `media` (`https://firebasestorage.googleapis.com/v0/b/<bucket>/o/<encodeURIComponent(path)>?alt=media&token=<token>`); live-piano notes and vocal notes are `notes.json` / `vocals.json` (no object: not computed yet);
- what is read is kept on the device (below) and valid exactly while its version and `createdAt` are the index's — at any age: token URLs do not run out. `createdAt` tells a track deleted and added again (the same content gets the same id, and version 1 again, with new media tokens) from the old one. A track missing from the index (brand new, or deleted on another device) is asked of the API, which forgets it here on a 404. Notes that are not computed yet are never kept (notes saved later, also on another device, leave the version as it is); notes saved here or found through the API are kept at the index's version and `createdAt`;
- every gap takes the API path below, as it was before the index (with its TTLs — a list kept here older than 6 h is asked again): the index failed (rules, network, SDK blocked — until another sign-in or a reload) or did not answer in 3 s; a file missing, unusable (`track.json` without audio in `media`) or unreadable. A Storage read is bounded: the SDK retries a network failure (no CORS, blocked, offline) for 4 s (`STORAGE_RETRY_MS`, not its default 2 min) and a read without an answer after 8 s (`STORAGE_READ_TIMEOUT_MS`) counts as failed. After a Storage read fails (anything but "object not found"), that kind of file (`track.json`, `notes.json`, `vocals.json`) is not read from Storage again this session, until a reload or another account (no retry storms). Missing rules or bucket CORS therefore cost at most one short wait per kind of file, then the app behaves as before; a missing backfill is the one gap the API path does not cover (above). A media download from Storage that fails does not re-probe the API (that would wake it). A token URL Storage refuses (403/404: made again with new tokens, a token revoked, `track.json` re-published at the same version) has the kept track forgotten and `track.json` read once more, else the track asked of the API, and the file downloaded from the URL that brings; once per track per session for the audio (`fetchTrackAudio`, also the player's recovery) and the stems (`fetchStem`) together, never in a loop.

**Cloud cache** (`src/lib/cloud/cache.ts`). The signed-in user's cloud library is kept on the device, so opening the site and replaying a song wake no Cloud Run instance. It lives in IndexedDB `chords-listener-cloud` (separate from the browser library `chords-listener`; no `local-` tracks in it). Every row is keyed by the account's uid. It is used only while `backend === 'cloud'` and someone is signed in, never for a local server or a guest. While the live library answers, what is kept is judged by version (above); on the API path, by age as follows. What is kept:
- the list: the live library's, for the next first paint; on the API path (`GET /tracks`) served from the device while younger than 6 h (`LIST_TTL_MS`, the same as a track). The home page shows it at once whatever its age and asks again in the background when stale. On the API path this device's own changes refresh it sooner: a finished job (also one started here that ended while the page was closed: the job list after a reload reports it as done), a track moved to the cloud, «Оновити» and «Спробувати ще раз» ask the cloud right away, and a change made on another device shows after the TTL or «Оновити»;
- opened tracks: read from Storage (with their `version` and token URLs, valid while that version and their `createdAt` are the index's), or from the API (`GET /tracks/{id}`, signed URLs included, no version): served for 6 h (`TRACK_TTL_MS`) on the API path, less than the 12 h a signed URL lives, so their `audioUrl` / `stemUrls` still play;
- the audio: the player plays the device copy as a Blob URL. Without one it streams the token URL (or the signed URL) and, once that can play through, downloads the file once in the background (Storage needs the bucket CORS for that). Total ≤ 300 MB (`AUDIO_BUDGET_BYTES`); the least recently played files go first;
- live-piano notes and vocal notes, once found (with the track's version and `createdAt` when the live library gave them).

What changes it:
- an edit or a reset replaces the kept track and its list entry (the API's answer, without a version: while the live library answers, the next open reads `track.json` again);
- a delete forgets the track everywhere. It is also remembered at once in localStorage (`src/lib/cloud/deleted.ts`, per uid, before anything is awaited — a page closed during the undo window may lose its IndexedDB write), so neither what is kept nor a list answer that set off before the delete brings it back; opening it asks the cloud. That note goes once a list asked after the delete no longer has the track, a list asked after the cloud confirmed the delete lists it again or a finished job makes the same id again (ids come from the content), or after 7 days. The live library's list does not use these notes: the index document goes with the track;
- opening a track the cloud no longer has (404, deleted on another device) forgets it here, list entry included;
- on the API path every list the cloud sends squares what is kept with it: a track it no longer lists (deleted elsewhere) is forgotten completely, a kept track it lists differently (renamed, edited, re-analysed elsewhere) loses its JSON. An empty answer, or one with fewer than half the tracks kept (the server sends one when it cannot read its storage), is saved stale and drops nothing: the next load asks again, and only the same answer then squares what is kept;
- a job seen finishing (`getJob`, or the job list after a reload) drops its track's JSON and vocal notes, so the next open asks again, and makes the kept list stale;
- a signed URL the cloud refuses (401) drops the track's JSON, and the track is asked again once for a fresh URL;
- a device copy that does not play is dropped for the signed URL.

The whole database is deleted on sign-out and when another account signs in (`src/lib/auth.ts`). Without IndexedDB, or with a broken or hanging one (each open is bounded to 2 s), every read is empty and every write does nothing.

### Keyboard shortcuts (global; ignore when focus is in input/textarea/contenteditable)

Shell agent: `Space` play/pause · `←/→` seek ∓5s · `Shift+←/→` previous/next chord change (uses `track.chords`) · `,`/`.` speed −/+ · `M` mute · `?` shortcuts help modal (lists ALL shortcuts below) · `Esc` close modal / clear loop.
Chords agent: `-`/`=` (also `[`/`]`) transpose −/+ · `0` reset transpose · `S` simplify toggle · `V` switch view (sheet → timeline → score) · `C` copy all (default format) · `F` follow-playhead toggle · `L` loop current bar / selection · `I` cycle instrument (guitar → bass → ukulele → piano → harmonium → handpan).
Tempo (`src/components/chords/tempo/useTempoHotkeys.ts`): `T` tap tempo (median of the last taps; a 2 s pause starts a new series) · `K` metronome on/off. Physical keys (`event.code`), no modifiers, also ignored while a modal dialog is open.
Chord sound (in `src/components/chords/hotkeys.ts`): `P` play the current chord (else the first chord of the bar selection, else the next one, else the last) on the selected instrument; same rules as the chord keys.

### Keep the screen on (`src/lib/wakeLock.ts`)

Setting `keepAwake` (local only, not synced; default `true`, also for settings saved before it existed): while the app is open and visible the screen does not dim or lock — on every page, a recording included. `useKeepScreenAwake(enabled)` is mounted once in `App.tsx`; the switch «Не вимикати екран» is in the toolbar settings (⚙). Screen Wake Lock API: `navigator.wakeLock.request('screen')` while the page is visible; the browser drops the lock when the page is hidden, it is requested again on `visibilitychange` → visible and on `pageshow`, released when the setting is turned off or the app unmounts. At most one request in flight and one lock held (a lock that arrives after the page was hidden or the setting turned off is released at once). A refused request (`NotAllowedError`: battery saver, no user activation) is retried once, on the next `pointerup` / `keydown` (a lifted finger is what counts as a user activation on touch screens); if that fails too, the next try is when the page is shown again. No API (older browsers, plain-http pages on the local network — it needs a secure context): nothing, no fallback, no errors or logs.

### Guide / tour (`src/lib/tour`, `src/components/tour`)

A guided tour over the real controls: a full-screen layer (`z-[75]`, above Modal / Floating `z-[60]` and the Toaster `z-[70]`, below the drop overlay `z-[80]`) dims the page ~60 % around a rounded cut-out (6 px padding, accent ring) and shows a bubble (title, 1–3 sentences, key chips on fine pointers, «3 / 10», «Назад» / «Далі» → «Готово» / «Пропустити»). It never opens menus or popovers. Design: `docs/superpowers/specs/2026-10-06-onboarding-tour-design.md`.

- **Tours** (`lib/tour/tours.ts`): Home (`home`, 8 steps), Song (`track` + `demo`, one seen flag, 12; 13 on phones), Score (the «Ноти» view, 5), Live keys (the «Живе фортепіано» panel, 4), Listen (`listen`, 6 for a tab; 4 for the microphone), YouTube (`capture`, 4 where the tab can be heard, else 2), fragment picker (`clip`, route `clip`: the window (touch variant), «Звідси», «Прослухати», «Розібрати акорди»; starts once the embedded player has loaded). A step names `data-tour` anchors (47 ids); its spotlight is the union of the visible ones. Conditions read flags the page reports (`useTourFlags`: `phone`, `touch`, `demo`, `cloudInvite`, `canListenInTab`, `listenMic`, `libraryEmpty` / `libraryList`, `hasChords`, `sheetView`, `scoreRendered`, `keysPanel`, `keysReady`); conditions and anchor presence are re-evaluated at every step change; steps without anchors and `centre` steps without their anchors are centred cards. Texts: `src/i18n/tour.ts` (`tour.<tour>.<step>.title` / `.text[.demo|.touch|.noTab|.mic]`).
- **Anchors**: `data-tour="<id>"` on existing elements, the first *visible* match wins (copies hidden for the other breakpoint are skipped); `data-tour-until="<selector>"` ends an anchor's box at its first match (a heading with its first row); `data-tour-avoid` keeps the bubble clear (the floating video); `data-tour-top` adds to the top inset (the video docked on phones). `components/tour/anchors.test.ts` checks every anchor exists in the code.
- **Auto-start** (`lib/tour/trigger.ts`, `components/tour/hooks.ts` `useTourTrigger(tourId, ready, recording)`): once per device, ~500 ms after the screen is ready (Home: connection settled, auth ready, library loaded or failed, no link / file on its way and an empty link field — `useTourBlock`; Song: track loaded; Score: header shown; Live keys: notes ready, never the demo; Listen / YouTube: capture phase `idle`, YouTube's player loaded) and the page is quiet (no `aria-modal`, `[role=menu]` or `[aria-expanded=true]`, no text being typed (an empty focused field does not count), the song not playing, no recording, the page visible). One tour at a time; a due tour waits and re-checks after the running one closes.
- **Behaviour**: starting on `track` / `demo` pauses the song and sets `followPaused`, restored on close; a recording keeps running. Any route change closes the tour unseen and drops chained tours. The root is `role="dialog"` + `aria-modal="true"` (the hotkeys, the home paste handler and `DropOverlay` stay quiet; a dropped file is still swallowed); → / ← / Enter / Space / Esc and Tab are handled in a capture listener on `window`; focus starts on «Далі», is trapped in the bubble and returns on close. An anchor counts as gone after 300 ms (a `centre` step stays as a card, others move on). Desktop: the bubble sits below or above the spotlight, ≥ 8 px above `--player-h`; phones (< 640 px) and short screens (< 500 px tall, e.g. a phone in landscape: centred, at most 640 px wide, the desktop steps) dock it at the bottom, with the spotlight scrolled above it; spotlights taller than the free area dock it too. `prefers-reduced-motion`: no transitions, no smooth scrolling.
- **Seen state** (`lib/tour/storage.ts`): `localStorage["chords-listener-tours"] = { "<tourId>": true }`, device-local (not in `SYNCED_KEYS`, nothing in Firestore), try/catch everywhere. «Готово», «Пропустити», Esc and running out of steps mark it seen; a tour with no available step does not open and is not marked.
- **Re-opening** («Інструкція» / "Guide"): the ⋯ menu (phones: every route, after the shortcuts; desktop: track pages), a desktop header `IconButton` (lucide `CircleHelp`) after the shortcuts button, and a line at the bottom of the shortcuts dialog (starts once the dialog has left the page). Hidden on `job` / `notFound` and while a song loads or fails. It runs the current screen's tour (track / demo: Score in «Ноти», else Song); with the live piano on screen, Live keys follows after «Готово» («Пропустити» / Esc end both).

### Tempo

The per-track correction factor `tempoFactors[track.id]` ∈ {0.5, 1, 2} (persisted locally, missing = 1) is applied in ONE place: `useEffectiveRhythm()` → `ChordModel.rhythm` (`src/lib/tempo/rhythm.ts`: ×2 inserts midpoints between beats and recomputes downbeats every `timeSignature` beats from the first downbeat; ×½ keeps every other beat). `ChordModel.bars`, the bar counter, timeline ticks, loops, copy formats (ChordPro `{tempo}`), the beat pulse and the metronome are all built from it; factor 1 = the detection unchanged. History cards show `tempo × factor`.

### Handpan

`instrument: 'handpan'` swaps the chord diagram for a top-down handpan (`src/components/chords/handpan/`, logic in `src/lib/handpan/`). Tone fields are sized by pitch like on a real instrument — the lowest the largest, ~1/√f (an octave up ≈ 0.71×, never under 0.55×; a narrower range on crowded rings so names still fit), octaves inferred when the scale has none (`handpanFieldSizes`, `handpanMidis` in `src/lib/handpan/pitches.ts`); the ding keeps its size. Settings (local only, not synced): `handpanScale` = `'custom'` (the user's own instrument) or a preset id (`d-kurd`, `d-celtic`, `cs-amara`, `e-amara`, `d-integral`, `f-low-pygmy`, `e-equinox`, `c-aegean`; unknown → `custom`); `handpanNotes` = `[ding, ...tone fields in physical order]`, each like `A` or `Bb3` (invalid → the default `A | D F A C G E C A`). Notes match by pitch class (`Bb` = `A#`). Song coverage = share of chord notes playable, weighted by duration; the best transposition is searched in −6..+6 (ties → smallest shift). The capo hint is replaced by this coverage hint while the handpan is selected.

### Piano

`instrument: 'piano'` shows the chord the way a pianist accompanies a song from its chords (rules researched from piano-method and teaching sources; `src/lib/diagrams/piano.ts`): the **left hand** plays the bass — the slash bass, else the root — alone, the one note of its pitch class in E2–D♯3 (MIDI 40–51); the **right hand** plays the chord in close position (within an octave) around middle C, the inversion whose notes average nearest E4 with every note in F3–C5 (MIDI 53–72; ties → root position; shared with the harmonium, `closeShape` in `src/lib/diagrams/hand.ts`), so the hand barely moves between chords: C = C3 | C4 E4 G4, F = F2 | C4 F4 A4, G = G2 | B3 D4 G4, Am = A2 | C4 E4 A4. A chord of four or more tones leaves out of the right hand the note the left hand plays (7ths: 3-5-7, `C7` = B♭3 E4 G4), then the fifth (9ths: 3-7-9, `C9` = D4 E4 B♭4); a slash chord gives its bass to the left hand and the plain chord to the right (`C/E` = E2 | C4 E4 G4). The diagram (`PianoChart`) shows the keys both hands use, C2–C5 (37 keys, key 0 = C2 = MIDI 36; widths sm / md / lg = 132 / 240 / 264 px), the left hand's key marked with a dot; the grand staff above writes each hand at the pitch it sounds (`staffChord`: right hand in the treble clef, the bass in the bass clef, spelled by thirds from the written root, a slash bass as written). The chord sound, the play-along and the score's simple level use the same voicing.

### Harmonium

`instrument: 'harmonium'` shows the Indian hand harmonium under its treble staff (`src/components/chords/diagrams/HarmoniumChart.tsx`, layout in `src/lib/diagrams/harmonium.ts`): its 37 keys C3–C6 (MIDI 48–84; 22 white + 15 black, black groups 2-3-2-3-2-3, a C at both ends; key index = MIDI − 48), seen from the player's seat — ivory keys with rounded front ends, slim black keys ~59 % of their length, a blue felt strip, a carved honey-wood panel with violet cut-outs (a simplified symmetric pattern, no text) and the dark bellows at the back, opening at the low end (hinged at the high end). The instrument keeps its real colours in both themes; only its outline follows the theme. Lit keys = `harmoniumVoicing(parsed)`, played the way harmonium players do: one right hand — the left pumps the bellows, so there is no separate bass and no bass marker — taking the chord in close position (all within an octave; a triad under fingers 1-3-5), and of its inversions the one whose notes centre nearest E4, the middle of the resting hand (thumb on middle C / Sa, fingers up to G4), so the hand barely moves between chords: `C` = C4 E4 G4, `F` = C4 F4 A4, `G` = B3 D4 G4, `Am` = C4 E4 A4, `G7` = B3 D4 F4 G4 (ties → root position). A slash bass stays the lowest note (`C/E` = E4 G4 C5, `C/G` = G3 C4 E4). Every shape stays within G3–F#5 (keys 7–30). A five-tone chord (a 9th, a slash bass outside the chord) leaves out its perfect fifth (`C9` = C D E Bb). The staff above it is the treble staff alone (`harmoniumStaff`: the same notes, spelled by chord degree, a slash bass as written; same scale as the grand staff, room down to G3). Widths sm / md / lg = 132 / 240 / 264 px (aspect ≈ 0.39); legend tiles ≥ 150 px like the piano's (two columns from a 340 px screen, so on a 360 px phone). The piano keeps its 2-octave keyboard (key 0 = C4). **Drone** (`src/lib/sound/drone.ts`, `components/chords/HarmoniumDrone.tsx`), like the harmonium's drone stops / a thumb held on Sa: the hero's «Дрон A» toggle (next to the tempo, harmonium only; setting `harmoniumDrone`, default off, local only) holds the song's tonic — `track.key` after `transpose` — on its key in the lowest octave (C3–B3, `droneMidi`) while the song plays: on with play, faded out (0.2 s) on pause, another instrument or closing the song, retuned on transposition; switched on while paused it sounds once (a key held 1.6 s). One harmonium note rendered with its key held 5 s, looped over 1–4.6 s with a 0.3 s equal-power crossfade baked in (`droneLoop`), swelling in over 0.25 s at the level of one chord key, on the harmonium bus (chord sound volume); chords never cut it and it lights no keys. Without a song key the toggle is disabled. While it is on, every click / key press resumes the audio, so play can start it.

### Chord sound (`src/lib/sound`)

Clicking a chord plays it (Web Audio, synthesized in the page; no samples, no dependencies). Settings (local only, not synced): `chordSound` (default `true`) turns on the *implicit* click-to-play; `chordSoundVolume` 0..1 (default 0.8, gain = v², for the clicked chords / keys and the drone; the play-along has its own `playAlongVolume`). Independent of the player's volume / mute.

- **Implicit** (only with `chordSound`): sheet slots and timeline blocks — they still seek, and sound only while paused (playing: the recording is heard there right away); legend tiles (with `chordSound` off a tile click copies the name; the tile's copy button always copies); the hero's current and next chord. **Explicit** (always): the popover's «Прослухати» button, every chord diagram (fretted chart → strum, on the bass an arpeggio; piano / harmonium key / handpan field → that one note — a piano key k = MIDI 60 + k, a harmonium key k = MIDI 48 + k; elsewhere on a keyboard / handpan diagram → the chord; voicing ‹ › never sound), `P`, the settings' test button. A brief ring / glow animates the element that was clicked; diagrams of the sounding chord light the keys / strings / fields while each note sounds (`useSoundingTargets`).
- **Notes = what the diagram shows**, for the display label (transpose / simplify / spelling applied). Piano: `staffChord(parsed, pianoVoicing(parsed))` (see Piano) — the left-hand bass (E2–D♯3) first, the right hand ~18 ms later and a bit softer; keys are held 2.6 s, then damped. Harmonium: the diagram's one-hand shape, every key pressed at once, held like the piano; they light the harmonium's own keys (target = MIDI − 48). Guitar / ukulele: the displayed chords-db voicing (same lookup and `voicings["instrument:label"]` index as `ChordDiagram`), its `midi` in string order, strummed from the first string (guitar gaps 20→16 ms, ukulele 15→13 ms, velocity falling ~4.5 % per string); a plain stacked voicing if chords-db has none. Bass: the displayed generated shape (`src/lib/diagrams/bass.ts` — every chord tone in one 4-fret position on E1 A1 D2 G2, the bass lowest, rising string by string; a perfect fifth may be left out when it does not fit; lowest position first, ≤ 6), arpeggiated low → high 110 ms apart. Handpan: only chord tones on the selected scale — the bass (slash bass, else root, else the lowest available tone) on its lowest field, each other tone once on the nearest field above, the root again if there is room; low → high, 70 ms apart. No playable tone → no sound + a hint toast. `N` plays nothing. Scales without octaves get inferred ones: the ding between A2 and G#3, the fields as the most compact ascending scale starting ≥ a minor third (preferably a fifth) above it, a duplicated pitch class an octave higher on the field nearer the player (default `A | D F A C G E C A` → `A2 | D4 F4 A4 C5 G4 E4 C4 A3`).
- **Voices**: piano = rebuilt from recordings of real grands, analysed partial by partial (Salamander Grand Piano v3 — Yamaha C5, Alexander Holm, CC-BY 3.0, every minor third, 16 velocity layers; University of Iowa MIS piano — Steinway B, pp / mf / ff): each partial's measured level every minor third (interpolated in dB) with the measured touch change per octave band (softer = darker and quieter); partials stretched by string stiffness (B ≈ 1e-4 in the bass, doubling every 8 semitones above C3) and stretch tuning (bass a few cents flat, treble sharp); the double decay — a fast prompt sound, then the aftersound 10–30 dB down — from one smooth model fitted to both pianos (median error 3 dB); the aftersound as two unison strings beating against the prompt one (~0.6 Hz at 1 kHz, ~1.5 Hz at 4 kHz); the hammer's knock on the soundboard (modal, swelling over ~20 ms, ~6 dB down per doubling of time, ~10 dB stronger on the top keys, as measured under their fundamentals); key up: dampers (upper partials faster, none from F6 up) and the action's soft thud; rendered offline per key × touch (0.02 steps) × hold × sample rate and cached with the plucks (LRU 48), stereo by pitch; guitar (steel) / ukulele (nylon) = Karplus-Strong plucks (allpass-tuned, pluck-position comb, frequency-dependent damping, body peaks + lowpass) rendered once per pitch × sample rate and cached (LRU 48); bass = the same renderer with a round-wound fingerstyle model (T60 ~4–6 s, dark damping, 90 Hz + 700 Hz pickup peaks); harmonium = rebuilt from a recording of a real Indian harmonium (Freesound #330410 by donyaquick, Yale Euterpea Studio, CC0; bass + male reeds): every key two reeds — the written pitch and a bass reed an octave below, each with its measured harmonic spectrum (every minor third, interpolated in dB) and the measured per-key detune between them (−8…+17.5 cents, the beating); reed speech ~17 periods (25–200 ms: the main fundamental first, its upper harmonics after, the bass reed last), the pallet click, air noise ~40 dB under the tone, the bellows' ±0.5 dB / ~1 cent wander, release −20 dB in ~28 ms; rendered offline per key × hold × sample rate and cached with the plucks (LRU 48); handpan = rebuilt from recordings of a real handpan (Freesound pack #33041 "HandPan 1st model" by GAMEDRIX974, CC0; a D minor handpan, every field struck once): each recorded note taken apart into its modes (subband ESPRIT — frequency, decay, level and phase), its 24 strongest kept and resynthesized, transposed from the nearest recorded tone field (E3–A5), every ding from the recorded D3 ding (T60 × 2^−0.3 per octave up); every tuned partial (fundamental, octave, compound fifth, double octave) is 2–4 split modes a few Hz apart (beating 1–8 Hz, T60 0.2–6.5 s), the octave starts 15–25 dB under the fundamental, blooms within ~100 ms and outlives it, the steel's untuned modes (~0.71, 0.84, 0.86–0.96, 1.03–1.2, 1.35 × f0, 10–25 dB down) ring mostly in the first few hundred ms; a ~3 ms dark strike noise (mostly under 1 kHz), a 1 ms rise; the recording's sympathetic ringing of its other fields is left out; −30 dB after ~1.1–2.1 s; rendered offline per pitch × ding / field × sample rate and cached with the plucks (LRU 48); a chord measures ~−16 dBFS RMS like before; panned by field position. A new chord fades the previous voices out in 70 ms (a single note replaces only a chord or the same note).
- **Play along** (`src/lib/sound/accompany.ts` — the patterns, pure; `src/components/chords/PlayAlong.tsx` — the player-bar toggle and the runtime): the toggle next to the metronome (the selected instrument's icon; setting `playAlong`, default off, local only; while on, its own volume slider beside it on wider screens, and always in the toolbar settings under the chord sound volume: `playAlongVolume` 0–200%, default 80%, local only, x² up to 100% and steeper above like the metronome's, independent of the chord sound volume) makes the selected instrument accompany the song while it plays, in its own style, with exactly the notes its diagrams show (`chordSoundNotes` of each displayed chord): guitar / ukulele strum down on every beat and up on the "and" of every beat but the first (D DU DU DU; the downbeat strongest; an upstroke = the top 4 strings high → low, 12 ms apart, softer); bass = the root on the downbeat and at every change, the fifth on beat 3 (4/4 and longer); piano = as pianists comp from a chord chart, the whole chord (left-hand bass + right hand) on beats 1 and 3 and at every change, the right hand alone on 2 and 4 (the bass rings on), in 3/4 a waltz (the bass alone on 1, the right hand on 2 and 3), keys held 1.6 s; harmonium = the chord's shape pressed when the chord comes and held until it changes (a looped key, released 40 ms before the next chord); handpan = the bass field on the downbeat and at every change, the other playable fields in turn on the other beats and every "and". Steps fall on the effective beat grid (the metronome's); a chord starting ≤ 80 ms after a beat counts from that beat; no chord = silence. Sync like the metronome: a 25 ms worker ticker plans the next 0.3 s on `MetronomeScheduler` (re-sync after a seek / loop wrap / speed change, the loop end held) against the audio clock being heard (the output timestamp, limiter included), while the player reports the position being heard — so a step is heard on the recording's beat (measured in the browser against a test clock: ±0.1 ms; after a seek, at 0.75× and 1.25× too). Steps are their own voices (`soundEngine.scheduleAt`): a step cuts the accompaniment's earlier notes ("all") or only re-strikes its own ("same"), a chord clicked meanwhile cuts them; pause / seek / off fade them out in 70 ms. The notes due in the next 4 s are rendered ahead, one per tick. While on, every click / key press resumes the audio, so pressing play starts it; the context is not suspended while it runs. Timing correction `playAlongOffsetMs` (−150…+150 ms in 5 ms steps, default 0, local only; positive = the instrument later; in the toolbar settings under the play-along volume, with ±5 ms steppers and a reset): the scheduler plans as if the song were that much earlier, a change eased in like clock drift (measured: +40 → +40.0 ms, −30 → −30.0 ms). Where the beats sit: the browser engine's grid is calibrated on six real recordings to their attacks (`BEAT_OFFSET_FRAMES` 0.1: −3…+5 ms, mean +0.7; it was 0.5 = 6–14 ms late), the server's neural grid measures 0…+6 ms. Known limit: after a seek in a compressed file the browser's own clock can be off the audio by up to ~1 frame (m4a up to −16 ms, mp3 up to ±47 ms, measured; WAV exact) until the next seek — playback from the start is exact.
- **Graph**: one lazily created `AudioContext({ latencyHint: 'interactive' })`, separate from the metronome: voices → their group's volume per instrument (chord sound: `chordSoundVolume`; play-along: `playAlongVolume`) → instrument bus (+ send to a small synthetic room reverb) → master → DynamicsCompressor limiter → destination. Created / resumed synchronously inside the gesture (plus a silent buffer for iOS); a mouse press on `[data-cw-sound]` warms it up before the click. Suspended after 15 s without sound; nothing runs while idle. Without Web Audio: silent, one info toast, no errors.
- **Live notes** (`src/lib/liveNotes.ts`): every played note is emitted once, when scheduled, with the `performance.now()` times it is heard (`start`) and released (`end`: piano / harmonium = key up; strings / handpan = faded to −30 dB). Times come from `getOutputTimestamp()` (waiting ≤ 250 ms for a live one after the context starts) or `currentTime + baseLatency + outputLatency`, plus the limiter's 6 ms lookahead. When a newer sound cuts a note, the same note (**same `midi` and `start`**) is emitted again with the earlier `end` (= when the new chord starts) — consumers should treat `(midi, start)` as the note's identity and keep the latest `end`. Notes scheduled after the cut get `end = start`.
- Dev builds expose `window.__chordSound` (`.stats`: plays, voices, the last live notes and their context times; `.renderOffline(request)` renders through the same graph for level checks).

### Live piano (`src/components/chords/piano`, `src/lib/transcription`)

With a keyboard instrument (`piano` or `harmonium`) a panel under the hero shows notes falling onto a keyboard whose keys go down in sync with the audio. On the piano it shows by default the song's chords as a pianist plays them along («Акорди», setting `liveKeysSource` = `'chords'`, local only): the play-along's piano pattern on the beat grid with the diagram's voicing — the left hand's bass on beats 1 and 3 and at changes, the right hand's chord on every beat (3/4: bass on 1, chord on 2 and 3) — each key held until its hand (left = below F3) strikes again or its chord ends, lifted 60 ms before a re-strike (`pianoShapeNotes` in `components/chords/piano/chordShapes.ts`; nothing is transcribed, so it also works on the demo); the subtitle says «Ліва рука — бас, права — акорд біля першої октави…». A switch in the panel's header, «Акорди | Ноти пісні», turns it to the recording's own transcribed notes (`'song'`, below) with the status, the recompute button and the voice offer. On the harmonium («Жива фісгармонія») the song is played the way a harmonium player accompanies it: instead of the transcribed notes, each displayed chord's diagram shape (`harmoniumVoicing`) goes down when the chord comes and is held, on the count, until the chord changes (`components/chords/piano/chordShapes.ts`; nothing is transcribed, so it works on the demo too; a no-chord stretch lifts the hand); the subtitle says so, the legend calls the coloured bars «Акорди», and neither the recompute button nor the offer to separate the voice is shown (a separated voice still shows as outlines). Settings (local only, not synced): `liveKeys` (default `true`; the panel's ✕ turns it off, the toolbar settings switch «Живе фортепіано» turns it — and, unless a keyboard is chosen, the piano — back on) and `syncOffsetMs` (−300..300, default 0, positive = keys light later).

- **TrackNotes** (`src/types.ts`): `{"version": 1, "engine": str (≤ 200), "notes": [[start, end, midi, velocity], …]}` — seconds rounded to ms, sorted by start; `midi` integer 21..108 (the 88 keys), `velocity` 0..1, `0 ≤ start < end ≤ duration + 1`, at most 300 000 notes, body ≤ 25 MB (`Settings.max_notes` / `max_notes_mb`). The server re-rounds, sorts and writes `data/tracks/<id>/notes.json` atomically (compact JSON) and serves it verbatim (`Cache-Control: no-cache`); an unreadable / unknown-version file counts as not computed. Notes are deleted with the track and kept by re-analysis, chord edits and reset (the audio is the same). PUT goes through the same local-only / cross-site guard and CORS as every write. Browser tracks (`local-…`) keep them in IndexedDB (`chords-listener` version 2, store `notes`, rows `{id, notes}`; the upgrade from version 1 only adds the store), deleted with the track. If saving fails (e.g. an older server without the endpoint) the notes live for the session.
- **Transcription** — once per track, in the page (`requestNotes(track, {force?})`, hook `useTrackNotes(track)`): memory cache (6 tracks) → saved notes (`api.getTrackNotes`) → `api.fetchTrackAudio` (the copy kept on the device for a cloud track, the server's `audioUrl`, or the IndexedDB blob) → `decodeAudioData` on a 22 050 Hz `OfflineAudioContext`, channels averaged → Spotify's **Basic Pitch** (Apache-2.0; `public/models/basic-pitch/` = the unmodified model of `@spotify/basic-pitch` 1.0.1 with LICENSE / NOTICE, loaded from `${BASE_URL}models/basic-pitch/model.json`) on slim TF.js 4.22 (core + converter + WebGL + CPU backends). A module worker runs it with WebGL through OffscreenCanvas (its shaders are compiled in parallel while the audio downloads); without WebGL in workers the page's WebGL runs it, yielding between windows; else the CPU backend in the worker. TF.js is only in the worker / a lazy chunk, never in the main bundle; the panel itself is lazy too. Windows of 43 844 samples every 36 164 (30-frame overlap, half trimmed per side) with exact per-window frame times; one window per call (~360 MB of GPU textures; ≈ 0.7 s per minute of audio on an M4 Pro, CPU ≈ 30 s per minute). Decoding = a port of basic-pitch's `outputToNotesPoly` (identical output, checked against the package in tests; heap-driven melodia trick, O(n log n)) with onset 0.5, frame 0.3, notes ≥ 80 ms, melodia trick and inferred onsets on; then parabolic sub-frame onset refinement, +4 ms onset shift (measured bias), merging per pitch (overlaps, double attacks, re-attacks weaker than 0.7 within 30 ms of the same pitch's end, onset-less continuations within 120 ms), dropping notes weaker than 0.4 (½ amplitude + ½ onset), velocity = that strength stretched over the song (95th percentile → 1). Progress: audio 0–0.04, decode → 0.1, model 0.1–0.96 (with the running count of notes found, decoded from what is evaluated so far), notes 0.97. One transcription at a time: another track's request stops it, and it stops 2.5 s after no panel shows its track. Accuracy / speed: `cd frontend && node scripts/eval-transcription.ts` (synthetic piano / plucked / fast clips with known notes, TF.js CPU in Node).
- **Sync**: every animation frame the panel reads `controller.getTime()` and smooths it with `LiveClock` (extrapolates with `performance.now()` × `playbackRate` between readings, folds fresh readings in at 20 %, never runs backwards, re-anchors at once on jumps > 120 ms ahead / 50 ms behind (seek, loop, stall), holds after play / a jump until the player's time moves; pause and rate changes apply on the next frame). Drawn time = clock + rate × (frame lead − `syncOffsetMs`), frame lead = the measured refresh interval (a frame reaches the screen one refresh later). Media elements report the position being heard (Chromium / Gecko / WebKit subtract the device output latency), so `AudioContext.outputLatency + baseLatency` is not added to the song — it is measured once (on opening the sync popover) and shown there as information. Preview notes from `onLiveNotes` light keys at their own `performance.now()` times with the same lead / offset, also while paused; `(midi, start)` identifies a note, a re-emitted one updates its `end` (`end = start` removes it).
- **Drawing**: one `<canvas>` (devicePixelRatio): a ~3 s falling-notes roll (black-key lanes, octave and bar lines, chord-change lines with the displayed labels) above a keyboard with real proportions (7 equal white keys per octave, black keys 0.58 × 0.63 at the 12-way split of the octave); pressed keys sink 2 px, take the pitch class colour (`--chord-N` by fifths, read from `<html>` and re-read on theme change) at a brightness from velocity, and flash for ~150 ms with a glow on every attack; a key that is down prints its note's name (the song's spelling, no octave) at its front when it fits. On the piano the keyboard fits the song (whole octaves, ≥ 4, ≤ 88 keys; outliers ignored); under 640 px ≤ 3 octaves around the most notes. On the harmonium it is always the instrument's own 37 keys C3–C6 (`HARMONIUM_RANGE`, ending on the top C; at every width) behind a blue felt strip. Notes outside the keys fold by octaves to the nearest edge octave with ▲ / ▼ marks. Song notes follow `transpose`. While paused the keys under the playhead (and attacks ≤ 80 ms later) stay down, dimmer. Animation frames run only while playing, while preview notes sound / glow, or once after a change; reduced motion = no roll, keys only. Accessible: `role="img"` + label, and a polite live region naming the keys down (≤ every 1.5 s). Test hook: `canvas.__livePiano` = `{time, playing, keys, range}` of the last drawn frame.

### Score — «Ноти» (`src/components/chords/score`, `src/lib/score`, `src/lib/vocals.ts`)

`view: 'score'` shows the song as sheet music drawn by OpenSheetMusicDisplay 2.x (BSD-3) from the MusicXML that is also exported: «Вокал» (the sung melody, when the server transcribed it) above «Фортепіано» (grand staff, the instruments' notes), chord symbols on top. OSMD + VexFlow (≈1.4 MB) and jsPDF + svg2pdf.js (≈0.5 MB) are lazy chunks only.

- **Time**: measures = the chord sheet's bars (`buildBarGrid` on the effective rhythm, so ×½ / ×2 apply); seconds → ticks piecewise linear between each bar's beat boundaries, a beat = 4 ticks (MusicXML divisions 4, a tick = a 16th). A short first bar is an implicit measure "0"; an incomplete last bar is padded (a long one split); other odd bars get a time-signature change.
- **Vocal part** (`lib/score/vocal.ts`) from VocalNotes: monophonic; slides / blips shorter than 0.55 of a 16th (≤ 130 ms) next to another note go to the neighbour nearest in pitch; onsets on the 16th grid (8th at the medium and simple levels) leaning to the 8th by 0.2 tick; the end is the rounded offset or onset + rounded length, whichever keeps both nearer to what was sung; overlaps cut; gaps < 1/8 closed (< 1/4 at medium / simple). Treble clef, treble-8vb (`clef-octave-change −1`) when the median is below C4.
- **Piano part** (`lib/score/piano.ts`) from TrackNotes: ghost notes dropped (velocity < 0.3, < 90 ms, < 40 % of the loudest note of the onset), onsets within 60 ms aligned, notes below A1 an octave up; hands split per beat by a Viterbi path over split points 48–72 (gap between pitch clusters, hand span ≤ an octave, ledger lines, near middle C, smooth); same onset in a hand = one chord, ≤ 4 notes (outer voices + loudest inner); a chord lasts until its longest note ends, never past the hand's next onset; short releases closed (< 1/8 or ≤ ¼ of the gap between onsets), releases before rests on 8ths. Medium level: 8th grid, RH ≤ 3 / LH ≤ 2 notes, stricter ghosts, a chord repeated within a beat is held.
- **Notation levels** (`ScoreOptions.level`): `full` «Складний» (16th grid, the piano part above), `medium` «Середній» (8th grid, the thinner piano texture), `simple` «Спрощений» — the piano part is the chord sheet, not the transcription (`chordPiano` in `lib/score/piano.ts`): each bar's displayed slot labels as the piano diagram's staff writes them (right hand = the diagram's right hand around middle C, a slash chord's plain chord; left hand = slash bass or root in E2–D♯3; spelled by thirds from the written root like `staffChord` — Gm is G B♭ D in any key — not from the key signature), struck at every chord change and again at every barline (no ties; a split long last bar goes on over its extra measure and is struck again there), lasting until the next change or the end of the slot; the same label repeated in a bar merges; N and unparsable labels are rests; velocity 0.7; `Score.pianoSource = 'chords'`; no piano part when the sheet has no chords. Vocals at `simple` are written as at `medium`. At `simple` the score view does not start the instruments' transcription (nor shows its progress) and exports do not wait for it; one already running keeps going, so the other levels get its notes.
- **Source**: with the track's `instruments` stem the piano notes are transcribed from it (`requestNotes({…, notesSource: 'instruments', loadAudio})`; cached per device in IndexedDB `chords-listener-stems`, newest 16 — the server keeps only the mix notes), else from the mix, minus the sung notes when they exist. The view, the live piano and exports show which source was used.
- **Chord symbols**: the sheet's bar slots (displayed labels: transpose / simplify / accidentals), written where the chord changes (in a split long last bar, beats past the time signature are in the extra measure); N.C. for no-chord ≥ 2 beats. Notes / rests are split (tied) at chord changes so every symbol sits on a note or rest of the top part.
- **Key / spelling** (`lib/score/spelling.ts`): the transposed track key (F♯/G♭, D♯m/E♭m by the spelling preference); notes on the line of fifths — diatonic as in the key, chromatic from [fifths−3, fifths+8] (major) / [−2, +9] (minor), the minor leading tone always raised.
- **Notation** (`lib/score/notation.ts`): split at barlines and into values that show the beat (dotted values where standard, syncopations inside a half bar, no dotted / syncopated rests, whole-measure rests), beams per beat with 16th hooks, explicit accidentals per measure and staff.
- **MusicXML** (`toMusicXml`): score-partwise 4.0, work-title, `creator type="composer"` = artist, credits (title, subtitle "Транскрипція: Chords Listener", composer), A4 defaults, metronome + `sound tempo`, `harmony` (root / kind / bass / degree; N.C. = kind `none`). Tests parse it back (DOMParser, jsdom), load it in OSMD and compare with `src/lib/score/__fixtures__/demo.musicxml`; it validates against the MusicXML XSD.
- **MIDI** (`toMidi`): SMF format 1, 480 PPQ; track 0 = title, key / time signatures and one tempo per beat taken from the beat times (the quantized notes play in time with the recording); tracks «Вокал» (Voice Oohs, channel 1), «Фортепіано RH» / «LH» (piano, channels 2 / 3); velocity = 24 + 103·v; UTF-8 names.
- **PDF** (`lib/score/pdf.ts`): OSMD lays out A4 portrait pages (1100 px wide ≈ a 7.6 mm staff), svg2pdf.js draws each page SVG as vectors into jsPDF; the text font is an embedded DejaVu Serif subset (Latin, Cyrillic, ♩ ♭ ♮ ♯; `src/lib/score/fonts/`, Bitstream Vera / DejaVu licence), also used by OSMD on screen. Page 1: title, credit, "Тональність · Темп", artist; every page: "Сторінка n з N".
- **Downloads** (`lib/score/download.ts`): «<title> — ноти.pdf|.musicxml|.mid» via a Blob URL on `<a download>` (iOS 13+, Android); without `download` a new tab; if that is blocked a toast offers «Відкрити». From the score header and the toolbar's copy menu (which loads / transcribes the notes first — not at the simple level — and never starts a vocal job).
- **View**: toggles Вокал / Фортепіано / Акорди and the «Складність нот» radio group Складний / Середній / Спрощений (local `chords-listener-score`, version 2; a v1 state's `simplified: true` becomes `medium`, otherwise `full`; an unknown stored level is read as `full`); the cursor follows the clock (interpolated between written notes, auto-scroll with `follow`, manual scrolling pauses it); clicking a note seeks there; phones get a smaller zoom and abbreviated part names; colours from the theme.
- **Vocals** (`lib/vocals.ts`): `GET /api/tracks/{id}/vocals` (404 = not yet), `POST …/vocals` → Job (`kind: 'vocals'`) polled every 1.5 s, not while the tab is hidden, and not at all when the job list already polls it (stages «Відділяю голос → Визначаю мелодію» from the job message), stems via `track.stemUrls[name]` when the server provides signed URLs, else `GET /api/tracks/{id}/stems/{name}` through `apiFetch`. Browser tracks / browser mode: "needs a server"; 501 / `features.vocals === false`: "not installed here". A finished job marks the loaded track `vocals: true, stems: [...]` without resetting playback.
- **Live piano**: same instrument notes (instruments stem when available); the sung melody as outlined bars in the ink colour and a dot on the sung key, toggle 🎤 (`liveVocals`, local). Under the panel title only what the user acts on: loading / recognition progress and errors; once the notes are there a legend (coloured = instruments, outlined = voice) while the melody is shown, or — notes from the full mix and the track says `vocals: false` where vocals can be transcribed — «Голос тут змішаний з музикою. Відокремити голос», which starts the vocal job (`startVocals`) and shows its progress. Showing the offer asks the server nothing.

### In-browser engine (`src/lib/engine`)

`analyzeInBrowser(file, onProgress?, { signal })` decodes with Web Audio on the main thread (22 050 Hz mono) and runs the DSP in a module Web Worker. It returns the same shape as the engine contract above (`engine: "chords-listener-web 1.0.0"`). Failures reject with `BrowserEngineError.code` ∈ `unsupported_format | too_long | too_large | analysis_failed` (same limits as the server: 30 min, 500 MB); an abort rejects with `signal.reason`. Accuracy tooling: `cd frontend && node scripts/eval-web-engine.ts --dir <synthetic songs>`.

## Design direction

Simple, calm, extremely usable; play-along first. Dark theme default (studio feel), light theme available. The current chord must be readable from 2 meters away. Chord blocks are colored by root around the **circle of fifths** (`--chord-N`, N = fifths index of root: C=0, G=1, D=2, A=3, E=4, B=5, F#=6, C#=7, G#=8, D#=9, A#=10, F=11) so related chords look related; minor = same hue, slightly darker/desaturated treatment. Fonts: `font-sans` Inter (UI), `font-display` Space Grotesk (chord names), `font-mono` JetBrains Mono (times). Motion: subtle, fast (≤200ms), respects `prefers-reduced-motion`. Every copy action gives a toast + inline check-mark feedback.

## Firebase (sign-in: the cloud on the hosted site, settings sync everywhere)

Project `build-chords-listener`, web app `chords-listener-web`. Signing in (email + password) keeps 11 UI preferences the same on every device and, on the hosted site, switches the API to the cloud (docs/CLOUD.md, "Where the API lives" above): the library then lives in the account. A local server (`./start.sh`, same origin) stays unauthenticated and never sees the account. Without an account, or with Firebase blocked or offline, the app works in browser mode; the home page invites to «Зареєструватися» / «Увійти». The one account dialog of the app is `components/account/AuthDialogHost` (`openAuthDialog`, `requestSignIn` in `src/lib/auth.ts`).

- **Synced keys** (`src/lib/syncedSettings.ts` ⇄ `isValidSettings` in `/firestore.rules`, keep both in sync): `simplify`, `accidentals`, `instrument` (`guitar|bass|ukulele|piano|harmonium|handpan`), `view` (`sheet|timeline|score`), `barsPerLine` (2|4|8), `follow`, `showDiagrams`, `copyFormat`, `theme`, `lang`, `showVideo`. Everything else (transpose, volume, speed, handpan notes/scale, metronome, tempo factors, server URL, chord sound, live piano, keep the screen on, harmonium drone, play along, its volume and timing) stays local. A new value for a synced key needs a rules change + deploy first; until then the client keeps it local and syncs the other keys. Deploy order for a new value: rules first (`firebase deploy --only firestore:rules`), then the client.
- **Data**: one doc `users/{uid}` = `{ email, createdAt, updatedAt, settings }`, owner-only read/write, strict schema (`/firestore.rules`). On the hosted site the cloud library adds the index `users/{uid}/tracks/{trackId}` (one document per track: the `TrackSummary` fields + `version` + `publishedAt`), written only by the cloud API and read by its owner with one collection query (`orderBy('createdAt', 'desc')`); track data, notes and vocal notes are read from Firebase Storage (`users/{uid}/tracks/{trackId}/{track.json, notes.json, vocals.json}`, owner-only `/storage.rules`). See "Live library" above and docs/CLOUD.md "Library in Firestore"; on any gap the client uses the cloud API as before.
- **Sync rules** (`src/lib/settingsSync.ts`): on sign-in the profile wins (except keys changed on this device while it was loading); local changes are pushed after 800 ms; changes from other devices arrive live; the first sign-in creates the profile from this device's settings; nothing is written before the server has been reached.
- **Loading**: `src/lib/auth.ts` (store `useAuth`, `startAuth()` mounted in `App.tsx`, `signIn/signUp/sendPasswordReset/signOut`) imports `src/lib/firebase.ts` (app + Auth) lazily; Firestore (`src/lib/firestore.ts`: one instance, memory cache only, for `settingsSync.ts` and the live library) loads only once someone is signed in; Storage (`firebase/storage`, `src/lib/cloud/storage.ts`) only for an upload or a read of the signed-in library. The main bundle contains no Firebase code.
- **UI**: `src/components/account/{AccountButton,AuthModal}.tsx`, strings in `src/i18n/account.ts`, error codes → keys in `src/lib/authErrors.ts`.
- **Config**: `/firebase.json` (auth providers, Firestore `(default)` in `eur3`, emulator ports), `/.firebaserc`, `/firestore.rules`, `/firestore.indexes.json`. Authorized domains: `localhost`, `shchadylotaras.github.io` (+ the default `*.firebaseapp.com` / `*.web.app`).
