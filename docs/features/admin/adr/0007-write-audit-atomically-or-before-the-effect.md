# 0007 — Write the audit record atomically with Firestore changes, and before any non-Firestore effect

- **Status:** Accepted
- **Date:** 2026-10-07
- **Deciders:** Тарас Щадило (Tech Lead) + Claude під час Socratic-проходу `design`

## Context

Інваріант CONTEXT: кожна дія адміністратора й кожен перегляд особистих даних завжди потрапляють у журнал; дія, яку не вдалося записати, не виконується, а дані, перегляд яких не вдалося записати, не показуються (AC-33, AC-33b). Частина змін живе у Firestore (ліміти, обмеження, видалення, налаштування), частина — поза ним (`quota.json` на GCS, обліковий запис Firebase Auth).

## Decision drivers

- AC-33 / AC-33b — без запису в журнал дія не виконується, дані не показуються.
- AC-10b — відхилені спроби теж у журналі.
- NFR «Зберігання журналу» — ≥ 365 днів, записи незмінні.

## Considered options

1. **Атомарно, де можна; інакше журнал перший** — batched write «зміна + журнал» для Firestore-змін; для ефектів поза Firestore — спершу журнал, потім дія, при невдачі — дописати «не застосовано».
2. **Завжди журнал перший** — один шаблон для всіх дій: журнал → зміна → за потреби «не застосовано».

## Decision outcome

**Chosen:** Option 1. Для більшості дій отримуємо справжню атомарність безкоштовно; для скидання квоти — гарантію «нема журналу → нема дії» і чесний слід, якщо дія не вдалася.

## Consequences

**Positive**
- Жодна зміна не оминає журнал.
- Перегляди (пошук, картка) — журнал перед відповіддю; при невдачі відповідь не віддається.
- Єдиний обовʼязковий шаблон для всіх адмінських обробників (§8).

**Negative**
- Для ефектів поза Firestore можливий запис «спробували, не застосовано» — журнал має його показувати.
- Два звернення до сховища для таких дій замість одного.

**Neutral**
- Журнал дописується лише сервером; у клієнтів і в адмінці немає шляху змінити чи видалити запис (AC-11).
