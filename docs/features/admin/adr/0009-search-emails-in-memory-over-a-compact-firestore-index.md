# 0009 — Search emails in memory over a compact sharded Firestore index, caught up incrementally from users

- **Status:** Accepted
- **Date:** 2026-10-07
- **Deciders:** Тарас Щадило (Tech Lead) + Claude під час Socratic-проходу `design`

## Context

Пошук користувача — за частиною email будь-де в адресі, без урахування регістру, від 3 символів (AC-03, AC-04). Firestore підтримує лише точний збіг і префікс. Документ `users/{uid}` з email створює сайт при реєстрації; сервер може ніколи не бачити користувача, який не запускав хмарних задач.

## Decision drivers

- NFR «Latency p95 пошук користувача» ≤ 1 с при 10 000 користувачів.
- NFR «Вартість перегляду адмінки» ≤ 200 читань на екран, незалежно від кількості користувачів.
- NFR «Повнота видалення» — 0 залишків email, зокрема в даних для пошуку.

## Considered options

1. **Компактний індекс у пам'яті** — кілька документів-шардів із парами uid → email (малими літерами), сервер читає їх цілком, кешує й шукає підрядок у пам'яті; перед пошуком дотягує нові документи `users` за позначкою часу створення.
2. **Триграми в документі довідника** — масив 3-символьних шматків email + запит `array-contains` і дофільтрування на сервері.

## Decision outcome

**Chosen:** Option 1. Пошук — 1–3 читання шардів + читання лише нових реєстрацій, незалежно від кількості збігів; триграми для поширених шматків («gma») зачіпали б майже всіх.

## Consequences

**Positive**
- Справжній пошук підрядка; передбачувана вартість.
- Видалення прибирає email з шарда в тій самій операції знеособлення.

**Negative**
- Індекс денормалізований: потрібне разове заповнення з `users` і підтримка при реєстрації/видаленні.
- Зміна email користувачем потрапляє в індекс лише при наступній повній синхронізації (фонова робота двічі на добу, ≤ 12 год) — прийнятий борг.
- Межа ~20 000 записів на шард (1 МБ на документ): більше користувачів — більше шардів.

**Neutral**
- Пошук за uid (точний збіг) лишається тривіальним доповненням.
